# AGENTS.md

## 项目总览

- 类似星露谷物语那种视角的坦克大战（俯视角/2D）。
- 玩家操控一个坦克；后续可能扩展为多人（网络同步/预测/回滚等）。
- Engine: Bevy.
- Keep changes small and shippable（改动要小、可交付、可运行）。

## Repo layout（仓库结构）

- `/tank`: 坦克相关（组件/预制件/生成与视觉装配）

## 预制件约定（Prefab conventions）

> 目标：单机可用，同时为多人/网络留出空间；避免把“渲染树”与“逻辑实体”强耦合。

### 默认方案（推荐）：逻辑与渲染分层（多人友好）

- **逻辑预制件（Logic Prefab）**：只生成“游戏逻辑/网络需要”的组件  
  - 例如：`Tank{team,hp,...}`、`Transform`（或 Position/Rotation）、碰撞/移动相关组件、以及未来的网络标记（NetworkId/Replicate 等）。
  - **不要**在逻辑预制件里 spawn `SpriteBundle` 或 children（Turret/Barrel）层级。
- **视觉装配（Visual Assembly）**：客户端/渲染侧通过系统自动补齐  
  - 例如：检测到 `Tank` 但没有 `TankVisual` 标记时，为其插入 `SpriteBundle` 并挂载 Turret/Barrel 子实体。
  - 视觉层可自由调整颜色/尺寸/层级，不影响网络同步协议。

适用场景：

- 单机：也可以沿用（逻辑+视觉照样生成，只是逻辑和视觉的代码分开）。
- 多人：服务器只跑逻辑，客户端本地生成视觉，减少同步负担、降低不一致风险。

### 备选方案：一体化 spawn（仅原型/小规模单机）

- `spawn_tank()` 里同时 spawn 逻辑 + Sprite + children 层级。
- 优点：开发最快、代码集中。
- 风险：多人时服务器/客户端耦合大；children/视觉 Transform 同步与回滚可能抖动；后期拆分会产生更大 diff。

> 默认选择：**逻辑与渲染分层**（上面“默认方案”）。除非任务明确要求快速原型且不考虑多人，才用“一体化 spawn”。

## 编码与改动规则（Coding rules）

- 尽量最小化 diff：能局部改就不要大范围重构。
- 未经明确要求，不要引入新的依赖、插件或第三方库。
- 优先遵循现有代码风格与目录约定；如果仓库里没有统一风格，就保持本次改动内部一致。
- 修改后确保项目能 `cargo run` 打开/运行。
- 若涉及资源加载，注意 Bevy 的 `assets/` 路径与 `AssetServer` 引用（路径大小写/相对路径一致）。

## 沟通输出要求（给 Codex 的要求）

- 任何不确定点：先给出 1-2 个方案对比（优缺点/风险），并说明你选择的默认方案。
- 对关键改动：写清楚：
  - **改了什么**
  - **为什么这样改**
  - **如何验证**（最少给出可执行的验证步骤）

### 验证清单（建议）

- `cargo check` / `cargo run` 能通过
- 坦克能生成且可见（如果本次改动涉及视觉装配）
- 逻辑组件存在且数值正确（hp/move_speed/turn_speed 等）
- 若引入“视觉装配标记”（如 `TankVisual`），确认不会重复生成

## 安全区/禁止改动（Safety / do-not-touch）

- 未经要求，不要修改 CI、发布配置（例如 `.github/`、release 脚本等）。
- 不要无理由重写大文件，避免巨大 diff。
- 不要随意改动项目全局设置（如窗口/渲染/输入映射等），除非任务明确需要，并在说明中列出改动项。
